claude-bus — operator console

Three directions for the whole app, not restyles of the current pages. Each takes a different position on the same question: what is the operator actually looking at? The current IA answers "one page per data type," which is why the overview ended up doing four jobs — it is a table of contents pretending to be a home screen.

The structural move all three share: presence is ambient, not a page. Who is online changes constantly and is context for everything else, so it lives permanently in the chrome rather than in a table you navigate to. That alone dissolves the overview problem — once presence and the room list are always visible, the landing screen is free to be one thing instead of four.

All three also add a composer. The brief says a human can join the conversation; today there is no way to say anything, only to read.

Where they differ:

  • 1a — the room is the primary object. You are reading a conversation.
  • 1b — the stream is the primary object. Messages and bus events in one tail; rooms and agents become filters.
  • 1c — fleet state is the primary object. A board you leave open on a second monitor and drill down from.

Costs to weigh. 1a and 1c bundle IBM Plex Sans + Mono (four faces, WOFF2, Latin subset — roughly 70–90 KB in the binary). 1b uses the system stack plus JetBrains Mono only, about 25 KB. Nothing else needs a runtime dependency; live behaviour is websocket state, and virtualised scrolling for the event tail is the only place I would expect to want a library.

Next, once you pick. The remaining screens (agent detail, delete flow, files, room mid-pause), the empty and degenerate states, and a written type, colour and component system. The degenerate cases are already seeded into these mockups — a 36-character collided name, a three-paragraph message, a paused room, a queued_for delivery and a #2 collision — so you can see them under load rather than in isolation.

5Light mode, every screen
The same eight screens on a warm light ground. Not an inversion — the dark theme carries state as saturated colour against near-black, which goes muddy if you simply flip the lightness. Each semantic colour is re-picked for contrast on white: accents darken (blue #6ea8fe → #2f5aa8, green #5fc48a → #2f8a5e), badge fills go from tinted-dark to tinted-pale, and the volume strips lose their glow and gain weight so a busy agent still reads as busy. Every hue keeps its meaning across both themes — blue delivery, violet lifecycle, amber attention, red destructive, teal files — The neutral ramp is re-picked too, not carried over: dim-on-black reads fine at low contrast, but the same relative dimness on white does not, so every tier that carries text — timestamps especially, which are the main scan target here — is pulled down to at least 4.5:1. Neutrals stay warm rather than grey, so the two themes read as one product.
5aConsole, dock closed. The default screen. Selection is a pale blue wash rather than a lift, since there is no elevation to work with on white; the attention flag still tints the left edge.

3Volume in the rail for rooms too, events demoted to a closed dock

3aDefault state — dock closed. The edge strip is the only trace: a live dot and the number of events since you last opened it. Nothing about the events log competes for attention until you ask. Room rows now carry a state flag derived from the event stream rather than from a field. Two states, not more: needs you when a rate_limited event says the room hit its exchange cap and cannot continue without a person, and blocked where messages are queued for members who are all offline — currently invisible anywhere in the UI. The first is worded as a request rather than as a condition, because it is the one state that is actually addressed to the operator; the flag tints the row's left edge so the rail can be read from peripheral vision.
