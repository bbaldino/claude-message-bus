# Console data layer (phase 2a)

## Context

The redesign handoff (`docs/ui-design-pass/handoff/`) replaces ten server-rendered
pages with a single console: presence in an always-visible left rail, the room as the
primary object, a collapsible events dock, and a composer.

Building that is five or six subsystems, not one. It is decomposed as:

| | Piece |
|---|---|
| **2a** | **Data layer — this spec.** API endpoints, aggregates, protocol additions, the observer socket, the typed client |
| 2b | Shell and room screen (3a, 3b) |
| 2c | Detail screens (4a–4f) |
| 2d | Composer |
| 2e | Light mode (5a–5h) |

2a comes first because the volume strip and the room state flags are the two places
where the design assumes data the bus does not currently produce, and both are
load-bearing for the rail, which appears on every screen. Discovering their cost
after the UI is written is the expensive ordering.

Phase 1 (already merged into this branch) built the infrastructure: a React/Vite
package under `ui/`, its bundle embedded in the binary and served at `/app`, one
endpoint `GET /api/agents`, and `ts-rs` generating TypeScript types from the Rust
structs.

## Scope

**In:** the endpoints, aggregates and protocol additions the console *shell* needs —
rail, transcript, events dock — plus the observer websocket and a typed client with
an observable store.

**Out:** any redesigned UI, the detail screens' endpoints (they land with 2c, being
trivial reads whose shapes are better decided against the screens that use them), and
the participant websocket (it lands with 2d, which builds the composer that needs it).

## Decisions

### The server derives the expensive parts

One rail-summary endpoint returns volume buckets, state flags and presence already
computed. Deriving buckets client-side would mean fetching an hour of messages for
every room to draw eight sparklines; server-side it is a `COUNT` grouped by a
five-minute bucket.

The server returns **data, not sentences**. A `blocked` flag carries
`{ queued, delivered, waiting_on }`; the client composes "waiting on caas · 2 queued,
0 delivered". The handoff specifies copy as final and design-owned, so a wording
change must not be a backend change.

### Push the instant things, poll the rail

The handoff describes one socket feeding everything. It also says the volume strip is
"scanned, not watched" and must not animate on update. Those pull apart, so:

- **Pushed:** new messages in the open room, agent presence, bus events. Delay here is
  visible and reads as broken.
- **Polled**, every ~25s: the rail summary. Buckets are five minutes wide; pushing
  them buys nothing a poll does not, and would mean the server deciding when an
  aggregate changed and diffing it.

### Protocol additions are opt-in

Rejected: a firehose where every observer receives presence and all events
automatically. It is less code, but `claude-bus tail` watches a single room and would
begin receiving fleet-wide traffic to discard. It would also turn the observer
invariant into "narrow for requests, wide for pushes".

Also rejected: a second transport (SSE) for events and presence. It leaves the
websocket protocol untouched but gives the bus two unrelated push mechanisms.

### Unread badges are client-side

Observers deliberately have no cursor — `reply_history` never moves one. Unread is the
console's own notion: last-seen message id per room in `localStorage`. This is correct
rather than a workaround: a viewer is not a subscriber, and a server-side cursor would
make the console a fleet participant appearing in `queued_for`.

## API surface

All reads, all following the pattern phase 1 established: DTOs defined in
`src/web/api.rs` rather than serialized store rows, camelCase on the wire, types
generated by `ts-rs`, errors as HTTP status codes with a JSON body.

### `GET /api/rail`

The one expensive aggregate, refreshed by the poll.

Per room: name, last activity, 12 five-minute volume buckets, members, and an optional
state flag with its supporting data. Per agent: name, host, version, online, last seen,
and 12 buckets of its own.

**Flag derivation is new logic, not a read:**

- `needs_you` — a `rate_limited` event indicates the room hit its exchange cap and
  cannot continue without a person. Carries the exchange count.
- `blocked` — messages are queued for members who are **all** offline. Carries
  `queued`, `delivered`, and the names waited on.

The handoff notes `blocked` is currently invisible anywhere in the UI: messages piling
up for agents that are all offline is a real failure mode with no surface today. This
endpoint gives it one.

There is deliberately **no `paused` flag**. An earlier design draft had one; the bus
has no such concept.

On a store failure this returns `500`, not an empty fleet. An empty rail renders as
"everything is quiet", which is the opposite of the truth when the database is down.

### `GET /api/rooms/{name}/messages?limit=&before=`

The transcript, paginated backwards for scrollback.

### `GET /api/events?room=&kind=&limit=`

The events dock. Omitting `room` gives the whole-bus scope — the capability that lets
the standalone events page be deleted.

`kind` narrows the **fetched history**, which matters for the whole-bus scope where the
table has no natural bound. It does not contradict the client-side live filtering below:
the fetch is narrowed at the source so the browser never pulls thousands of rows it
would immediately discard, while the *push* stream stays unfiltered and is filtered in
the browser, so toggling a checkbox re-renders instead of round-tripping.

### `GET /api/meta`

Host and version, for the top bar pill ("hardac · 0.3.3"). Small, but it does not
belong inside the rail aggregate.

## Protocol additions

Two commands an observer may send, two pushes it may receive. Every other `ToBus`
variant continues to be rejected in `handle_observer`, preserving the property its
comment describes: a future command must not "accidentally become observer-usable just
by falling through".

| Command | Effect |
|---|---|
| `ToBus::WatchPresence` | Subscribe to agent connect/disconnect |
| `ToBus::WatchEvents { room: Option<String> }` | Subscribe to events; `None` is the whole bus |

| Push | Payload |
|---|---|
| `FromBus::Presence` | `{ name, host, online, last_seen }` |
| `FromBus::Event` | `{ id, kind, agent, room, detail, created_at }` |

**Where they originate.** Presence hooks the two sites that already mutate the
registry: `attach` in the register path and `detach` in the disconnect path. Events
hook `Store::append_event`, the single funnel every event kind already passes through
— so a kind added later cannot silently fail to appear in the dock.

**The dock's `kinds ▾` filter stays client-side.** Filtering pushed events in the
browser is trivial; putting it in the protocol would mean a round trip per checkbox.

## TypeScript data layer

Three modules under `ui/src/data/`, one job each.

**`api.ts`** — typed fetch wrappers over the generated types, one per endpoint.
Non-2xx throws. Nothing swallows an error into an empty result; that is the trap the
phase-1 review caught in `/api/agents`.

**`live.ts`** — the observer socket. Opens `/ws`, sends `Observe`, then
`WatchPresence` and `WatchEvents`, and `Watch` for the open room as selection changes.
Owns reconnect with backoff, and exposes the connection state that drives the top
bar's `live` pill — which the handoff requires to show amber `reconnecting` and red
`disconnected`, because it is the websocket state and not a decoration.

**`store.ts`** — the observable state everything reads: rail summary, transcript,
event log, presence, connection state. Applies pushes, and re-fetches the rail on its
timer.

A single store rather than per-screen hooks, because presence and events feed the
rail, the dock, the unseen badge and the transcript at once; per-component fetching
would open several subscriptions to one stream and let them disagree about what is
current.

The store appends new messages but does **not** decide to scroll: the handoff requires
"3 new below" rather than yanking a reader who has scrolled up, so the pin-to-bottom
choice belongs to the component that owns the scroll region.

## Testing

**Rust integration tests** (`tests/web.rs` style — a real bus over a real socket).
The three that matter are the derived ones, because they are the only genuinely new
logic in this phase:

- seed messages at known timestamps; assert bucket counts land in the correct
  five-minute slots
- seed a `rate_limited` event; assert `needs_you` with the right exchange count
- take every member offline with messages queued; assert `blocked` with the right
  `queued` / `delivered` / `waiting_on`

**Protocol tests** (`tests/bus.rs` style): an observer that subscribes receives
presence and events; **an observer that does not subscribe receives neither.** The
second is the `tail` guarantee and the reason opt-in was chosen over a firehose.

**vitest against `store.ts`** with a mocked socket: a pushed event lands in the log, a
presence push flips an agent, a dropped socket surfaces as `disconnected`, a reconnect
restores.

**One end-to-end smoke check:** the throwaway `/app` screen rendering the rail summary
as raw JSON. Not a design — proof the path carries real data. It is deleted in 2b when
the real rail replaces it, keeping the phase-1 pattern where the visible artifact is
disposable and the plumbing is what ships.

## Consequences accepted

- The rail is up to ~25s stale in its volume buckets and flags. Deliberate: buckets are
  five minutes wide.
- `/api/rail` recomputes aggregates on every poll rather than caching. At this fleet
  size that is a handful of indexed `COUNT`s; caching can come if it ever shows up in a
  profile.
- Two websocket connections will exist once 2d lands. Only the observer half is built
  here.
- The detail screens have no endpoints yet, so 2c carries slightly more than a pure UI
  phase.
